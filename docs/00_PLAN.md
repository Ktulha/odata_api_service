# API-сервер для работы с 1С по ODATA — план разработки

## Архитектура (общая схема)

```
Клиенты (только GET)                      1С (OData.publish)
     │  Bearer token                             ▲
     ▼                                           │ только sync-воркер ходит в 1С
┌─────────────────────── Роль: app ──────────────────────┐
│  FastAPI                                             │
│  ├ AuthMiddleware (проверка bearer при ЛЮБОМ запросе) │
│  ├ Data API: /api/v1/{entity}  (реестр разрешенных)   │
│  └ Admin API: /admin/v1/*      (роли, токены, cron…)  │
└───────────────┬────────────────────────────────────────┘
                ▼
        Собственная БД (PostgreSQL)  ◄── все запросы API только сюда
                ▲
┌────────── Отдельная роль: worker ──────────┐
│  Синхронизатор: scheduler (APScheduler)    │
│  + OData-клиент к 1С, upsert в БД          │
└────────────────────────────────────────────┘
```

**Принципы:**
1. Прямые OData-запросы клиентов невозможны — API принимает только фиксированный набор маршрутов; entity берётся из реестра, а не из URL «как есть».
2. Все данные читаются из собственной БД. 1С трогает только worker во время синхронизации.
3. Доступные сущности ограничены реестром (`is_active`). Если сущность запрещена — она **не кешируется вообще**, ссылки на неё тоже недоступны и в вывод не попадают.
4. Роли: `role ↔ entity` (набор сущностей). Bearer-токен привязан к роли(ам), проверка при любом запросе.
5. Админка — отдельный слой `/admin/v1/*` со своим типом токена (ADMIN): настройка ролей, глобальный/по-ролям доступ сущностей, генерация/revocation токенов, расписание синхронизации, просмотр логов, ручное обновление сущностей.

## Пошаговый план работ

| Шаг | Содержание | Статус |
|-----|-----------|--------|
| 1 | Обсуждение архитектуры, утверждение стека и плана | ▶ текущий |
| 2 | Каркас проекта, конфиг (pydantic-settings), docker-compose (PG) | ⬜ |
| 3 | Модели БД: registry, roles, tokens, sync_jobs, logs | ⬜ |
| 4 | Миграции Alembic | ⬜ |
| 5 | Auth-слой: проверка bearer, роли, зависимость доступа к сущности | ⬜ |
| 6 | Data API: список сущностей + универсальный GET-ридер (фильтр/пагинация/expand с проверкой запретов) | ⬜ |
| 7 | OData-клиент к 1С (httpx, токен 1С, пагинация) | ⬜ |
| 8 | Синхронизатор: загрузка → upsert в БД, правило «запрещено → не кешируем» | ⬜ |
| 9 | Планировщик (cron по сущностям), ручное обновление из админки | ⬜ |
| 10 | Admin API: CRUD ролей/сущностей, токены, расписание | ⬜ |
| 11 | Логирование запросов и событий, просмотр логов в админке | ⬜ |
| 12 | Тесты, edge-cases (запрет сущности → 403 и отсутствие в expand) | ⬜ |

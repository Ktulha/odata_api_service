# Q4: Синтаксис фильтров и параметров запроса (обсуждение)

## Запрос пользователя (эскиз)

```
$filter{Ref_Key in [,,,], Description like 'халат' and Description like 'махровый'}
```

## Что не так с эскизом и как это исправить

### 1. Тело $metadata-ответа 1С содержит поля только из основной таблицы
`ДополнительныеРеквизиты[].Значение`, `@navigationLinkUrl` — вырезаются при загрузке (решение ранее). Фильтр работает **только по колонкам боевой таблицы** + FK-колонки `*_Key`.

### 2. `like` в OData пишется иначе
OData-стандарт: `contains(Description,'халат')` или `Description eq '...'`. Наш вариант для удобства:

| Пользователь хочет | Пишем в API |
|---|---|
| Подстрока без регистра | `Description ~ 'халат'` (наш sugar → `lower(col) LIKE '%халат%'`) |
| Точное совпадение | `Description = 'халат'` |
| В списке значений | `Ref_Key in (guid'...', guid'...')` или короткая форма `Ref_Key = any([...])` |
| И/ИЛИ | `and`, `or` (скобки разрешены) |
| Пусто/не пусто | `Артикул is null`, `Штрихкод is not null` |
| Числа/дата | `Вес > 0`, `ДатаИзменения ge 2025-01-01T00:00:00Z` |

### 3. Почему `{...}` вместо `(...)`
URL-безопасность: фигурные скобки не нужно экранировать, читаемость выше. Но `$filter=(a)and(b)` каноничнее. **Предложение:** принимаем обе формы, внутри — стандартный синтаксис OData-подобных выражений.

### 4. Динамические ссылки (`ИсточникОбеспечения_Key/_Type`)
Фильтр по ним: `ИсточникОбеспечения_Key = guid'...' AND ИсточникОбеспечения_Type = 'Catalog_Номенклатура'` — две колонки, операторы обычные. Отдельного синтаксиса не нужно.

### 5. Ссылки на запрещённые сущности
Если `Catalog_Секрет` запрещена ролью — фильтр `Секрет_Key = ...` возвращает **403** (поле существует, но недоступно), а не пустую выборку. Так пользователь понимает причину.

## Предлагаемый итоговый формат параметра

```
GET /api/v1/data/Catalog_Номенклатура?
    $filter=Description ~ 'халат' and (IsFolder = false or Code in ('НФ-1','НФ-2'))
    &$select=Ref_Key,Description,Артикул
    &$orderby=ДатаИзменения desc
    &$top=50&$skip=0&$count=true
```

Параметры: `$filter`, `$select`, `$orderby`, `$top`, `$skip`, `$count` — все начинаются с `$` (как OData), чтобы не смешивать с нашими (`links=full`).

## Реализация (для утверждения)

1. **Ленер+парсер** (~200 строк): токенизация (идентификаторы с кириллицей, строки `'...'`, числа, даты, `guid'...'`, операторы `eq/ne/gt/ge/lt/le/=/<>/~/in/is/and/or/not`, скобки).
2. **Компилятор в SQLAlchemy**: AST → `.where()`. Строки — параметризовано (SQL-injection impossible). Поля сверяются с реестром до компиляции → неизвестное поле = 400 с ясным сообщением.
3. **Ограничения**: глубина вложенности ≤ 8; длина ≤ 2000 симв.; без функций кроме `contains()/startswith()/endswith()` (sugar для `~`).
4. Ошибки парсинга → `400 {"errors":[{"code":"filter_parse","message":"...","position":N}]}` — позиция в строке фильтра.

## Открытые вопросы (по одному)

**Q4-a (текущий):** Принимаем ли наш sugar-оператор `~` (подстрока, регистронезависимо) **вместе** со стандартными `eq/ne/gt/lt/ge/le/in/is null`, или строго OData (`contains(...)`, без `~`)?
- а) оба (рекомендую: `~` для людей, `contains()` для совместимости);
- б) только OData-канон;
- в) только упрощённый (`=`,`~`,`in`,`is null`,`and/or`).

**Q4-b (следующий):** `$select` — разрешаем ли выбирать любые колонки, или только whitelist из настроек сущности (быстрые поля для UI)?

**Q4-c:** `$expand` в API — нужен ли вообще (раз данные уже в БД, клиент может сделать второй запрос к связанной сущности по ключам), или добавляем `include=<link_name>` с JOIN ради удобства?
